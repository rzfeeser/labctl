# labctl

A command-line tool for operating the Alta3 Claude and 5G lab environment from the NOC VM.

## Author

Maintained by [rzfeeser](https://github.com/rzfeeser).

## Objective

`labctl` lets students run documented environment commands without repeatedly switching between virtual machines.

The tool:

- Reads named commands from `actions.json`.
- Connects to the appropriate VM through SSH.
- Provides help describing each action, its impact, and its prerequisites.
- Requests confirmation for actions marked as changes.
- Records command execution in a local audit file.

The execution path is:

```text
Student on NOC → labctl → SSH → Target VM → Terminal output
```

`labctl` makes no Claude API calls. It is an operator tool that supports the applications built throughout the course.

Application-specific dashboards, workers, approval gates, fault timers, and investigation records remain managed by their respective application controllers.

## Installing

### Requirements

Run the installer as the `student` user on the **NOC VM**.

The environment must already provide:

- Bash, Git, curl, and Python 3.
- The `open5gs-noc` service account.
- Its SSH key at `/var/lib/open5gs-noc/.ssh/id_ed25519`.
- Working hostname resolution for `core`, `ueransim`, and `ims`.
- The classroom SSH and sudo permissions.

Installing `labctl` does not configure these prerequisites.

### Download the Installer

Download the script so you can inspect it before running it:

```bash
curl --fail --location --show-error \
  --output ~/labctl-install.sh \
  https://raw.githubusercontent.com/rzfeeser/labctl/main/install.sh
```

Read the installer:

```bash
less ~/labctl-install.sh
```

Press **q** to exit.

### Run the Installer

The current installer clones the repository into `~/labctl`.

**If that directory already exists, stop and inspect it first.** The current installer does not reliably handle repeat installations: it attempts another clone and may continue using the existing files if cloning fails.

For a fresh installation:

```bash
if [ -e "$HOME/labctl" ] || [ -L "$HOME/labctl" ]; then
    echo "STOP: ~/labctl already exists; inspect it before installing."
else
    bash ~/labctl-install.sh
fi
```

Do not run the installer with `sudo`. It installs into your home directory.

Read the output and resolve any installation error before continuing.

### Update the Current Terminal

The installer adds the personal command directory to `.bashrc` for future Bash terminals. Apply it to the current terminal too:

```bash
export PATH="$HOME/.local/bin:$PATH"
hash -r
command -v labctl
labctl help
```

The command path should be:

```text
/home/student/.local/bin/labctl
```

### Installed Locations

| Location | Purpose |
|---|---|
| `~/labctl/` | Downloaded Git repository |
| `~/.local/share/labctl/labctl.py` | Installed Python runner |
| `~/.local/share/labctl/actions.json` | Bundled command catalog |
| `~/.local/bin/labctl` | Command link |
| `~/.config/labctl/catalogs/` | Registered project catalogs |
| `~/.local/state/labctl/actions.jsonl` | Operator execution log |
| `~/.local/share/labctl/HELP.md` | Help document generated by `labctl docs` |

Keep the installed Python runner and `actions.json` together. The program finds its catalog relative to its own location.

### Updating

Updating the Git checkout does **not** automatically update the installed copies.

Inspect your checkout before pulling:

```bash
cd ~/labctl
git status
git remote -v
```

After reviewing and preserving any local changes:

```bash
git pull --ff-only
```

Stop if Git reports an error. Back up the installed files, then copy the updated repository files into place:

```bash
cp -a "$HOME/.local/share/labctl" \
  "$HOME/.local/share/labctl-backup-$(date +%Y%m%dT%H%M%S)-$$"

install -m 755 ~/labctl/labctl.py ~/.local/share/labctl/labctl.py
install -m 644 ~/labctl/actions.json ~/.local/share/labctl/actions.json

labctl --version
labctl docs
```

Existing registered project catalogs remain separate. They can override a bundled command family, so review them when troubleshooting unexpected behavior after an update.

## How to Use

### Start with Help

```bash
labctl help
```

This explains syntax, examples, command families, prerequisites, recovery considerations, and application controllers.

List the available actions:

```bash
labctl list
```

Inspect a common action without executing it:

```bash
labctl help reconnect-ran
```

Inspect an action belonging to a particular lab:

```bash
labctl help subscriber check-ue3
labctl help capstone-ims emergency-off
```

### Run Common Commands

Common actions use:

```text
labctl ACTION
```

For example:

```bash
labctl core-status
labctl ue-status
labctl ue1-status
labctl ue1-sessions
labctl ims-status
```

These gather different observations. A running service does not establish successful registration, an active session, or working traffic.

### Use Command Families

Lab-specific actions use:

```text
labctl FAMILY ACTION
```

Examples:

```bash
labctl subscriber check-ue3
labctl specialist phone-processes
labctl capstone-data data-status
```

Families preserve the session names, paths, and helper behavior used by their corresponding labs.

Do not substitute one phone family for another. For example, `specialist` and `capstone-ims` may operate different tmux sessions and evidence files.

**An action being listed does not mean its prerequisites are installed.** Some commands require scripts, configuration, or phone sessions created during the relevant lab. Read the action's help first.

### Run an Environment Change

Actions marked **CHANGE** request confirmation.

For example, inspect the RAN reconnection action before deciding to run it:

```bash
labctl help reconnect-ran
```

When you intend to interrupt radio connectivity and reconnect it:

```bash
labctl reconnect-ran
```

Type `yes` at the confirmation prompt.

Some remote IMS helpers request an additional confirmation of their own.

`--yes` skips the runner's confirmation when explicitly supplied by an operator. It is not authenticated approval and must not be used to bypass an application's approval workflow.

### Understand Results

- **`COMMAND_COMPLETED`** means the command returned successfully.
- **`FAILED_OR_INTERRUPTED`** means execution failed or was interrupted. Remote changes may have partially completed.
- A lone **`STARTED`** entry may mean the process stopped before recording an outcome.

None of these states proves end-to-end service health.

After a change, collect the registration, session, or traffic evidence required by the exercise.

The runner does not automatically retry failed operations.

### Register a Project Catalog

Some labs provide an additional JSON catalog:

```bash
labctl register /absolute/path/to/lab_actions.json
```

Registration saves a snapshot and binds relative helper uploads to that catalog's project directory. It does not execute the actions.

After reviewing changes to a previously registered catalog:

```bash
labctl register /absolute/path/to/lab_actions.json --replace
```

A registered catalog takes precedence over a bundled family with the same name.

Catalogs contain executable shell commands. Review them as carefully as application code.

### Generate the Complete Help Document

```bash
labctl docs
less ~/.local/share/labctl/HELP.md
```

Press **q** to exit.

Regenerate the document after changing or registering catalogs.

### Inspect the Execution Log

```bash
tail -n 20 ~/.local/state/labctl/actions.jsonl
```

This student-owned log supports troubleshooting. It is not tamper-resistant approval evidence.

### Troubleshooting

**Command not found**

```bash
export PATH="$HOME/.local/bin:$PATH"
hash -r
type -a labctl
```

**Unknown action**

```bash
labctl help
labctl list
```

Check the family and action names.

**SSH or sudo failure**

Confirm that you are on NOC:

```bash
hostname
```

Inspect connectivity using:

```bash
labctl doctor
```

This runs remote hostname and noninteractive sudo checks. It does not restart services.

**Missing helper or tmux session**

Read the action's prerequisites and complete the corresponding lab setup. Installing the catalog does not create every remote helper or session.

**A change timed out**

Inspect current state before trying again. The remote operation may have partially completed.

### Execution Boundaries

`labctl` is an operator convenience, not a security sandbox.

- JSON metadata does not prove that a shell command is read-only.
- SSH and sudo permissions determine what commands can execute.
- Confirmation prompts are not a replacement for authenticated approval gates.
- An agent with unrestricted shell access may be able to invoke this tool.
- The classroom SSH configuration uses `StrictHostKeyChecking=no`; production deployments should verify host keys.

Keep application workflows separate. Use each lab's controller for its dashboards, workers, fault ownership, timers, baselines, approval records, and reports.
